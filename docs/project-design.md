# 企业级多平台智能代码评审与研发效能平台

## 产品与工程设计规范 v1.0

---

## 1. 项目概述

### 1.1 项目定位
一个**多平台、自动化、可量化、可配置**的智能代码评审中心。  
定位为研发质量与产出可观测性平台，而非简单的 PR 评论机器人。

### 1.2 核心价值
- **风险左移**：在 PR 合并前自动发现安全漏洞、逻辑 Bug、性能隐患、边界问题、依赖风险。
- **规范内建**：企业可自定义审查规范知识库，AI 严格按规范评审。
- **无感接入**：通过 Webhook 或 API 触发，自动运行。
- **可观测**：提供跨仓库、跨成员的提交活跃度、质量趋势、问题分布仪表盘。
- **自适应**：对于超大函数/文件，智能降级为结构评审，建议拆分重构。

### 1.3 适用场景
- 团队同时使用 GitHub、GitLab、Gitee 等多平台，需要统一评审标准。
- 期望将代码数据保留在企业内网，支持私有化模型部署。
- 需要对历史评审记录进行回溯、分析，生成成员代码质量雷达图。

## 2. 术语定义

| 术语 | 说明 |
|------|------|
| 平台 | GitHub、GitLab、Gitee 等 Git 托管服务 |
| 项目 | 在系统内注册的一个代码仓库，关联一个平台仓库 |
| PR | Pull Request / Merge Request，统一称为 PR |
| 评审 | AI 对一次 PR 的检查过程，产出 Findings |
| Finding | 一条具体问题，包含位置、类别、严重性、建议 |
| 规范 / 规则 | 企业自定义的代码审查标准，存储于知识库 |
| 超大代码块 | 单个函数/方法超出预设 Token 阈值的代码片段 |
| 结构评审 | 不逐行检查代码内容，仅分析结构指标并给出重构建议 |

## 3. 技术架构与技术栈

### 3.1 整体架构分层
系统采用**异步解耦、无状态计算、存储下沉**的架构原则，分为六层：
- **接入层**：统一处理多源 Webhook，负责签名验证、流量整形、协议适配。
- **消息队列与任务层**：将事件转化为持久化任务，实现削峰、解耦、可靠投递。
- **AI 评审引擎层**：基于 LangGraph 构建有状态、可观测、可中断/重试的评审流水线。
- **平台 API 网关层**：抽象多 Git 平台交互，统一限流、重试与错误处理。
- **数据与存储层**：关系型数据库 + 缓存 + 对象存储，支撑读写分离和历史归档。
- **管理后台与 API 层**：为前端提供数据服务，集成权限与审计。

### 3.2 技术栈详情

#### 后端
- **语言**：Python 3.11+
- **Web 框架**：FastAPI（异步、高性能，适配 Webhook 高并发）
- **任务队列**：Celery + Redis 或 ARQ（用于异步化 AI 评审任务）
- **消息队列**：Redis Stream 或 RabbitMQ（持久化、消费者组、死信队列）
- **数据库**：PostgreSQL 15+（主存储，支持 pgvector 扩展）
- **缓存**：Redis 7+
- **ORM**：SQLAlchemy 2.0 (async) + Alembic
- **对象存储**：MinIO / Amazon S3（原始事件、评审报告）
- **AI 编排**：LangChain + LangGraph（构建有状态的评审流水线）
- **代码解析**：tree-sitter（AST 分析与指标提取）
- **向量数据库**：pgvector（与 PostgreSQL 集成）或 Milvus Lite
- **配置管理**：Pydantic Settings（环境变量加载与验证）
- **日志与追踪**：OpenTelemetry（链路追踪），结构化 JSON 日志

#### AI 模型
- **主模型**：deepseek-v4-flash / deepseek-v4-pro（用于安全、Bug 等高价值维度的审查）
- **经济模型**：deepseek-v4-flash / Claude 3.0 Haiku（用于规范、风格等维度）
- **私有化选项**：支持 vLLM 部署开源模型（如 Llama 3、Qwen 2 等），确保代码数据不出企业网络
- **嵌入模型**：text-embedding-3-small 或 BGE-M3（用于规范知识库的向量检索）

#### 前端
- **框架**：React 18+ + TypeScript
- **构建工具**：Vite
- **样式**：Tailwind CSS
- **组件库**：shadcn/ui + Radix Themes
- **图表**：Recharts 或 Tremor
- **状态管理**：TanStack Query（服务端状态） + Zustand（客户端状态）
- **路由**：React Router v6
- **Diff 展示**：react-diff-viewer 或自研组件

#### 基础设施与运维
- **容器化**：Docker Compose（开发/中小规模部署），Kubernetes（大规模生产）
- **监控与告警**：Prometheus + Grafana（指标），Loki（日志），Tempo（追踪）
- **CI/CD**：GitHub Actions / GitLab CI
- **密钥管理**：HashiCorp Vault 或云平台 Secret Manager（用于 Token、Webhook Secret 等敏感信息）

## 4. 功能性需求

### 4.1 仓库接入与事件获取

系统支持两种方式获取 PR 事件：**Webhook 自动触发**（主要）与 **API 手动触发**（补充）。二者共用同一评审任务管道。

#### 4.1.1 Webhook 自动触发
- 用户在管理后台为项目配置 Webhook。
- 系统自动生成唯一 `project_id` 和 `webhook_secret`，提供完整 Webhook URL。
- 支持事件：`pull_request`（opened、synchronize、reopened）。
- 平台适配：
  - GitHub：验证 `X-Hub-Signature-256`，事件头 `X-GitHub-Event: pull_request`
  - GitLab：验证 `X-Gitlab-Token`，事件头 `X-Gitlab-Event: Merge Request Hook`
  - Gitee：验证 `X-Gitee-Token`，事件体 `action` 字段

#### 4.1.2 API 手动触发
- 提供内部 REST API，允许管理员或 CI 系统发起指定 PR 的评审。
- 请求体包含 `project_id` 和 `pr_number`，权限校验后进入正常评审流程。
- 用于 Webhook 失败后的补偿，或历史 PR 批量回审。

### 4.2 AI 评审流水线

一次完整的评审包含以下步骤，必须可追踪、可中断、可恢复。

#### 4.2.1 上下文获取
- 拉取 PR 完整 Diff（过滤二进制文件）。
- 对每个被修改的函数/方法，按需获取目标分支中完整源代码（最多上溯 200 行），作为审查上下文。

#### 4.2.2 规范加载
- 根据项目配置的规范版本，从知识库中检索与当前变更最相关的规则。
- 检索方式：以文件路径、函数名、引入的库名作为查询，向量相似度检索 Top-5 条规则，注入每个维度的检查 Prompt。

#### 4.2.3 代码分块与大小判断
- 使用 GPT-4 tokenizer 预估每个函数的 Token 数。
- 阈值设定（可配置）：
  - `chunk_normal_max`：1500 Tokens
  - `chunk_oversized_min`：2000 Tokens
- 分级：
  - **正常块**：≤ 1500
  - **边界块**：1500 ~ 2000
  - **超大块**：> 2000

#### 4.2.4 分路径处理

**路径 A：正常块 & 边界块 → 详细评审**
- 并行执行五个维度的检查：
  1. 安全漏洞（注入、XSS、权限、敏感信息泄露、不安全反序列化等）
  2. Bug 风险（空指针、逻辑错误、资源未释放、竞态条件）
  3. 性能与边界（N+1 查询、无限循环、不合理递归、异常未处理）
  4. 代码规范（命名、函数长度、圈复杂度、SOLID 原则，严格结合知识库）
  5. 依赖安全（解析依赖声明文件，对比漏洞库，标记已知 CVE）
- 每个维度返回结构化 Findings。

**路径 B：超大块 → 结构评审**
- 使用 AST 工具计算：圈复杂度、函数行数、参数数量、嵌套层级。
- 若任一指标超过硬阈值（圈复杂度>20，行数>200，参数>5），生成类别为 `structure`，严重性为 `warning` 的建议，描述违反指标及规范编号，建议拆分函数。
- 无论指标如何，超大块必须进行最小化安全检查：检查函数签名、返回类型及可见输入点是否存在高危模式（eval、exec、明文密码等）。
- 超大块不进行风格、性能等维度详细检查。

#### 4.2.5 结果聚合与发布决策
- 合并所有 Finding，去重。
- 发布策略：
  - 若存在 `severity=critical` 或 `severity=warning` 的 Finding 数量 > 5：
    - 生成详细评审报告（Markdown + HTML），上传至对象存储。
    - 在 PR 中发布摘要评论：评审总分、严重问题数量、各类问题统计、报告链接。
  - 否则：
    - 直接在 PR 中发布行级评论（对应代码行的具体建议）。
- 报告链接须携带临时访问令牌（有效期 7 天，可配置），避免暴露后台入口。
- 所有评论以系统配置的机器人身份发布。

### 4.3 管理后台功能

#### 4.3.1 仪表盘
- 全局概览卡片：接入仓库数、今日评审数、AI 建议采纳率。
- 30 天提交与代码行变更趋势图（可切换仓库筛选）。
- 问题分布饼图：按类别（安全、Bug、性能、规范、依赖、结构）展示。
- 时间范围选择器（7天/30天/90天）。

#### 4.3.2 仓库管理
- 项目列表字段：仓库名、平台图标、Webhook 状态、最近评审时间。
- “添加仓库”按钮进入 Hook 配置向导。
- 每仓库可：编辑、禁用、重设 Secret、手动触发全量规范刷新。

#### 4.3.3 Hook 配置向导
- 步骤 1：选择平台。
- 步骤 2：输入仓库 URL 或组织/仓库名。
- 步骤 3：生成 Webhook URL、Secret，展示推荐事件列表。
- 步骤 4：图文操作指引（平台截图 + 高亮填写位置）。
- 步骤 5：“测试连接”按钮，验证通过后状态改为“已连接”。

#### 4.3.4 评审记录
- 筛选：仓库、作者、日期、状态、评分区间。
- 列表字段：PR 编号、标题、作者、时间、AI 评分、问题总数、报告链接。
- 点击进入评审详情页。

#### 4.3.5 评审详情页
- 左侧文件树，右侧统一 Diff 视图（支持 Unified/Split）。
- Finding 在对应行高亮，点击显示：类别、严重性、描述、建议、关联规范条目。
- 开发者可对每条 Finding 标记“采纳”或“无效”，实时更新采纳率。
- 若存在详细报告，顶部提供“查看完整报告”按钮。

#### 4.3.6 成员分析
- 成员列表支持搜索。
- 成员详情：
  - 雷达图维度：安全性、Bug 防范、性能意识、规范遵循、依赖管理。
  - 常见问题标签云。
  - 提交活跃度柱状图（按周）。
  - 历史评审得分曲线。

#### 4.3.7 规范知识库管理
- 规范列表，可按标签、语言、严重性过滤。
- 每条规范包含：内容、示例代码、适用语言、标签。
- 版本管理：修改生成新版本，可设置生效版本，支持回滚。
- 冲突检测：新规则与已有规则矛盾时提示。
- 支持批量导入/导出为 YAML/JSON。

#### 4.3.8 依赖风险面板
- 以项目为维度列出存在已知 CVE 的依赖。
- 字段：依赖名称、版本、漏洞编号、CVSS 评分、修复版本、受影响项目。
- 支持手动触发全量依赖扫描。

### 4.4 API 触发接口

提供内部 RESTful API（需认证）：
- `POST /api/v1/projects/{project_id}/reviews` 手动触发评审，Body: `{ "pr_number": <int> }`，返回 `{ "task_id": "<uuid>" }`
- `GET /api/v1/projects/{project_id}/reviews/{task_id}` 查询任务状态，返回 `{ "status": "pending|running|completed|failed", "result_url": "<url>" }`
- 所有接口必须验证 JWT 或 API Key，并记录审计日志。

## 5. 非功能性需求

### 5.1 稳定性与容错

- **Webhook 接收**：无状态多副本，5 秒内返回 200；验签失败返回 403；事件 ID 60 秒内去重。
- **消息队列**：持久化，消费者组模式，死信队列（重试 3 次失败转入）。
- **Worker 容错**：优雅关闭，检查点序列化至 Redis；以 PR `head_sha` 为幂等键，缓存结果。
- **外部服务降级与熔断**：
  - LLM 调用：30s 超时，重试 1 次，连续 5 次失败熔断 2 分钟，定时 Job 重扫。
  - Git 平台 API：令牌桶限流不超过官方频率 70%。
  - 全局降级开关：可暂停所有自动评论，仅生成后台报告。

### 5.2 性能指标

- Webhook 接收延迟 P99 < 500ms。
- 正常规模 PR（文件数<20，变更<500行）3 分钟内完成评论。
- 后台 API 查询 P95 < 500ms，统计接口允许最大 2s。
- 报告生成 30 秒内完成。

### 5.3 安全性

- **凭证管理**：Token、Secret 使用 AES-256 加密存储或托管至 Vault，日志禁止输出明文。支持定期轮换和手动失效。
- **代码数据保护**：HTTPS 传输；数据库和对象存储中代码内容加密（可选）；支持内网部署与私有模型，确保代码不出企业边界。数据保留策略可配置，默认 90 天归档。
- **访问控制**：后台强制登录，支持 OIDC/SAML；权限至少分超管、项目管理员、查看者；开发者仅见本人统计；报告临时 Token 有时效和范围限制。
- **审计**：记录所有敏感操作，日志保存至少 180 天，可导出。

### 5.4 可观测性

- 结构化 JSON 日志，携带 `trace_id`。
- 指标暴露：Webhook 请求速率、验签失败数、队列深度、任务处理时长、LLM 调用成功率、评论成功率。
- 全链路追踪：Webhook → 任务 → LLM → 外部 API。
- 告警：
  - 队列积压 > 1000 持续 5 分钟 → 通知运维。
  - LLM 失败率 > 10% → 通知 AI 服务管理员。
  - 某仓库连续 3 次签名验证失败 → 通知项目管理员。

### 5.5 成本控制

- 单次评审 Token 上限 15,000（含输入输出）。
- 每项目可配每日/每月 Token 预算，超额暂停并通知。
- 模型分级：安全/Bug 用高质量模型，规范/风格用性价比模型。
- 相同 `head_sha` 缓存 7 天。
- 仅有 `.md`、文档字符串变更的 PR 可配置跳过。

## 6. 数据规范

### 6.1 时间字段强制要求

**所有数据库表必须包含以下两个字段，由系统自动维护：**
- `create_time`：记录创建时间，禁止更新。
- `update_time`：记录每次修改时间，行更新时自动刷新。

ORM 层启用自动时间戳，数据库层辅以触发器保证强制一致。

### 6.2 其他数据原则

- 主键使用 UUID v4。
- 评分等数值字段明确范围与精度（如评分 0-100 整数）。
- 枚举字段在代码中定义常量，数据库存储字符串。
- 关键实体优先使用软删除（`is_deleted` 字段）。

## 7. 项目自身代码规范

### 7.1 后端 Python 规范
- 严格遵循 PEP 8，使用 `black` 格式化（行宽 100），`mypy` 静态检查 strict 模式。
- 所有公共函数/方法必须包含类型注解和 Google 风格 docstring。
- 异步与同步分离：Web 处理用 `async/await`，AI 调用在后台线程池或队列执行。
- 禁止裸 `except`，自定义异常层次，所有外部调用捕获并转换。
- 配置使用 Pydantic Settings 加载，严格验证。
- 关键组件通过依赖注入组装，方便测试。
- 测试要求：单元测试覆盖率 ≥ 80%（核心逻辑），集成测试覆盖 Webhook、队列、数据库。

### 7.2 前端 React 规范
- 容器组件与展示组件分离，单一职责。
- 命名：PascalCase 组件，`use` 前缀 Hooks。
- 状态：服务端状态用 TanStack Query，客户端临时状态用 Zustand，避免 prop drilling 深度 > 3。
- 样式：优先 Tailwind utility class，`shadcn/ui` 组件保持默认 variant，不随意覆写核心样式。
- 可访问性：ARIA 标签，WCAG AA 对比度。
- 性能：长列表虚拟化，图片懒加载，路由级 Code Split。

### 7.3 API 设计规范
- RESTful 风格，URL 小写连字符。
- 请求/响应 JSON，时间 ISO 8601。
- 错误格式统一：`{"error": {"code": "...", "message": "...", "details": []}}`
- 分页参数 `page`、`page_size`，响应包含 `total`、`page`、`page_size`、`items`。

### 7.4 Git 工作流
- 分支：`main` 保护，`feature/xxx`、`fix/xxx`。
- Commit 遵循 Conventional Commits (`feat:`, `fix:`, `chore:`, `docs:`)。
- 合并需 CI 通过 + 至少一人 Review。
- 敏感信息绝不提交，使用 `.env.example` 说明。

### 7.5 文档要求
- `README.md` 说明项目定位、快速开始、架构图链接。
- `docs/` 目录存放架构设计、接口文档、部署手册。
- 重要设计决策添加 ADR 记录。
